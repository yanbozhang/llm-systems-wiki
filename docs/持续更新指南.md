# 持续更新指南

本指南把来源扫描、知识编纂和个人复习分成三条可追踪的流程。2026-10-24的中央清单包含七模块、45主题和135知识点；这是内容覆盖快照，不代表135项都已完成真实模型实验。课程、知识点、源码和练习的对应关系见[系统学习资源指南](系统学习资源指南.md)，十个方案的实现边界见[Agent开源方案导读](Agent开源方案导读.md)。

## 每周轮换以清单为准

星期来自[模块清单](../knowledge/modules.json)，每个模块的候选集合来自[主题清单](../knowledge/topics.json)。下表按当前文件中的顺序列出主题；新增、移动或删除主题后重新计算数量，不把表中的数字写进调度逻辑。

| 上海时间 | 模块 | 本次快照主题数 / 知识点数 | 模块内轮换顺序 |
| --- | --- | --- | --- |
| 周一 | 模型网络 | 4 / 12 | transformer → attention-heads → position → ffn-norm |
| 周二 | 训练 | 4 / 12 | pretraining → sft → preference → policy-optimization |
| 周三 | 推理 | 4 / 12 | prefill-decode → kv-cache → cache-scheduling → inference-frameworks |
| 周四 | Harness | 6 / 18 | agent-loop → context → memory → tools-skills → langgraph → autogen |
| 周五 | 知识库 | 4 / 12 | rag → ingestion → hybrid-search → graph-wiki |
| 周六 | 业务Agent | 12 / 36 | task-loop → gui-agent → coding-agent → agent-evaluation → openhands → swe-agent → aider → mobile-agent → app-agent → ui-tars → codex-cli → claude-code |
| 周日 | Benchmark | 11 / 33 | benchmark-protocol → benchmark-metrics → benchmark-contamination → benchmark-general → benchmark-reasoning-code → benchmark-multimodal → benchmark-agents → benchmark-rag → benchmark-judge → benchmark-systems → benchmark-robustness；同时保留跨模块复盘 |

当前[wiki_tool.py](../scripts/wiki_tool.py)中的 `plan` 函数以2026-10-19为周序起点。设当天为d、模块为m，其清单筛选结果为有序序列T_m，数量为N_m，则周序w为日期差除以7后向下取整，选择下标为 `w % N_m`。例如首周日2026-10-25选择benchmark-protocol，下一周日选择benchmark-metrics；第一轮覆盖Harness、业务Agent、Benchmark分别需要6、12、11次该模块的每周时段。按当前非空清单持续排课，12周可以让每个主题至少出现一次；这不是同时重回全部起点的联合周期，也不是读者掌握全部知识所需时间。

计划只提供当天主题的首个learning_objective和主题deliverable，没有逐知识点游标、完成记录或自动补课能力。日期推进会继续轮换，即使上次没有学完。维护者应按稳定topic ID、unit ID记录积压，禁止用“本周排到过”替代“已完成”。主题数量变化会改变取模结果，应保留计划日期、清单基线和选中ID；重要更正可人工插队，但原定主题要进入补课记录。

## 来源扫描产生什么

[每日工作流](../.github/workflows/daily.yml)计划在上海时间08:00、UTC 00:00运行，GitHub调度可能延迟。它使用默认分支的维护代码，按[订阅清单](../sources/manifest/feeds.json)顺序抓取公开源；`parse_feed`只提取条目身份、标题、链接和更新时间，将候选标为 `pending_read`、读取范围标为 `feed_metadata`。它没有读取论文全文、比较源码语义或改写正式主题。[wiki_tool.py](../scripts/wiki_tool.py)中的 `parse_feed` 和 `discover`

| 扫描结果 | 精确含义 | 接下来要做的工作 |
| --- | --- | --- |
| changed | 发现未见元数据候选，且本轮没有订阅失败 | 阅读正文并判断是否影响现有知识点；不能直接更新结论 |
| unchanged | 所有配置订阅检查成功，当前窗口内无新元数据候选 | 继续复习；不能保证上游全文、默认分支或全部历史都未变 |
| partial_failure | 部分订阅失败；成功订阅仍可能产生候选 | 分别审阅已有候选和失败记录，不把整轮当作“无变化” |
| failed | 本轮全部订阅检查失败 | 保留失败范围，安排回查；没有依据撤回原知识 |

`discover`为每个成功源更新checked，失败源保留旧检查点；partial_failure并不丢弃成功源的进展。候选身份由元数据规范化后计算，因此同一条目标题或更新时间改变也可能形成新候选；这个哈希不是正文指纹。正文内悄悄更正而订阅元数据不变，则可能完全不被扫描发现。

候选历史保存在 `updates/candidates` 分支：`runs`保存逐轮结果，`latest.json`显示最近状态，`state.json`保存去重与检查点，`study-plan.json`记录当天主题，`baseline.txt`标明运行代码基线。脚本依次写入轮次记录、最近结果、状态，工作流再保存候选分支；抓取成功、写入文件、远端持久化是三个不同结果。远端保存失败时，运行附件可用于恢复线索，不能声称检查点已同步。正式知识以默认分支为准，候选分支其他文件可能沿用旧基线。[wiki_tool.py](../scripts/wiki_tool.py)中的 `main` 落盘分支

## 从候选到真正内容更新

编纂的最小单位是一条有条件的认识：绑定一个知识点、明确旧说法和新依据，并给出能检查它的例子。先在阅读记录中形成下列材料，完成语义核验后再交整合者修改正式清单。这些是维护流程要求，不是现有巡检脚本已实现的功能。

| 阶段 | 必须留下的材料 | 可以推进的条件 |
| --- | --- | --- |
| 识别影响 | 候选URL、来源ID、topic ID / unit ID、旧page_version | 说明可能改变的定义、公式、实现条件或练习；只改发布日期的候选可留作观察 |
| 读取原文 | 论文版本与章节、官方说明读取范围、源码完整commit SHA及函数 | 实际读到相关正文；摘要、目录和跳转链接不足以支持实现结论 |
| 对照旧页 | 原说法、新证据、保留条件、冲突或缺口 | 分开论文抽象、当前代码分支和本库教学模型，不用新README覆盖历史论文语境 |
| 推导与反例 | 符号和单位、手算输入输出、正常例和失效例 | 说明何时结论不成立，例如分母为空、回调结束但业务失败、旧缓存身份不兼容 |
| 修订学习单元 | 公式、代码、专属结构图、完整示例入口、验证性质 | 各项表达同一机制；新增教学校验不能被写成上游已有保证 |
| 独立核验 | 语义复核意见、适用测试结果及代码基线，或明确的未执行项 | 章节完整和测试成功都不能替代来源支持；真实实验另有协议 |
| 整合发布 | 受影响声明、关系、能力目标、学习路径和变化说明 | 由整合者核对全局引用后发布；分工写作不越权改中央文件 |

来源版本遵守[编纂规范](../schema/编纂规范.md)：本库 `version`表示实际文本快照，`native_version`表示论文修订或源码commit，采集日期不能冒充发表日期。URL不可读、正文改变、资料撤回是不同事件；出现冲突时保留原版本及更正链，不能静默覆盖历史身份。

例如，若GraphRAG更新了同标题文档的识别方式，先比较所读 `get_delta_docs`与调用方怎样消费返回值，再检查[来源接入与版本管理](../wiki/topics/来源接入与版本管理.md)的分类和练习。仅凭README中的“增量更新”，不足以声称已有正文更正会自动被索引。若Ragas变化涉及平均精度分母，除了[混合检索与重排](../wiki/topics/混合检索与重排.md)的候选漏斗，还要复核[RAG检索与回答评测](../wiki/topics/RAG检索与回答评测.md)的AP、召回与裁判口径。

## 一次主题学习如何落实到三个知识点

一次模块时段先确定主题，再按[知识点清单](../knowledge/units.json)读取该主题的全部unit ID及命名函数。当前每主题有三个知识点；日后数量变化时以清单为准。不要只完成计划输出的第一个目标，也不要为赶轮换而将未完成项标成已掌握。

每个知识点各做一轮：先不看答案写问题和预期，再读课程相关内容与固定来源；画出计算或状态流，手算一个小输入；打开对应教学函数核对输入、分支和输出；最后设计只改变一个条件的反例。可以先完成一项再继续其余项，跨天时保留未完成unit ID。时间分配由读者基础决定，固定时长不是通过标准。

一条学习记录至少包含：topic ID / unit ID、page_version、来源版本、示例文件和函数、手算输入、预期输出、失效条件、实际验证方式、结果证据、下次复习日期。记录存于个人学习区，与公共内容成熟度分开；公共编纂不覆盖他人笔记。`worked`只表示页面含可检查教学材料，`designed`表示真实实践尚未执行；命名函数的UT记录单独关联，不会自动将整篇升级为reproduced。

按主题三点完成后，再写一段贯通解释。例如学完缓存分页，要能从逻辑token地址推到物理块、说明一次调度怎样受两种预算限制，再说明前缀树分裂与锁定如何影响复用。分别背出三个函数名不等于理解它们的状态依赖。

## 复习从回忆、变式到跨模块迁移

下面是本库建议的复习安排，尚无学习效果实验支持，不是已经部署的提醒服务。

| 时机 | 本次要做的事 | 留下的证据与补课条件 |
| --- | --- | --- |
| 当次结束 | 合上正文，写出核心公式或转移、单位及失效条件 | 错误标在具体unit ID；说不清分母或状态身份就保留“待复习” |
| 约一天后 | 不看示例重做原手算，再核对答案 | 记录错在定义、代数、索引、协议还是条件；不能只记“看过” |
| 下次周日 | 为本周一点更换输入或边界，连到当天Benchmark口径 | 例如长尾超时、重复调用、解析失败；周日仍保留原定Benchmark时段 |
| 约一个月后或来源变更后 | 用新例子迁移到另一模块，复核原版本条件 | 页面版本变化后重审受影响点，不要求无差别重学全部内容 |

迁移任务可以是“GQA缓存估算 → 分页实际分配 → TTFT/TPOT测量”，也可以是“RRF排序 → 上下文选择 → 声明忠实度”，或“工具调用身份 → 检查点恢复 → Agent预算内成功”。每条路径都要指出哪些量可由教学输入直接计算，哪些需要真实模型、设备或人工标注。

## 验证证据不能混用

| 验证层 | 回答的问题 | 不能证明什么 |
| --- | --- | --- |
| 文档与清单结构 | 链接、章节、ID、函数入口是否对应 | 引用是否支持语义结论、算法是否正确 |
| 人工推导与静态阅读 | 小例子的分母、维度、状态与反例是否一致 | 实际程序执行、并发和运行环境行为 |
| 教学函数UT | 给定简化输入的数学性质、错误分支、状态不变量是否成立 | 上游完整框架或大模型真实任务效果 |
| 框架集成实验 | 固定环境下真实接口、持久化、恢复和执行是否吻合 | 换模型、换设备或换负载后的普遍收益 |
| 任务评测与正式基准 | 固定数据、预算和评分协议下表现如何 | 自动推广到其他任务；自测合格也不等于正式MLPerf发布 |

作者提交示例函数、输入契约、待验证性质及已知限制，并明确哪些验证尚未执行；维护者组织独立语义复核、代码验证和CI检查。项目的课程结构入口为 `python scripts/wiki_tool.py check --curriculum`，每次验收应保存实际结果及对应代码基线。CI检查结构，评审者检查来源支持与结论条件；两类职责不能互相替代。

涉及评测时，保留任务分母、失败和超时、重试预算、随机性、模型及依赖版本、逐样本记录。引用存在不能证明语义支持；模型自报完成不能证明业务终态；图检查点不能保证外部副作用恰好一次。这三类错误应分别在检索、业务Agent和Harness复习中暴露。

## 周日与月度整合

周日先推进清单指定的Benchmark主题，再复盘本周材料：是否有未读候选混入结论、失败来源被误记为无更新、练习遗漏边界、已更正来源仍被派生声明使用。每个发现登记受影响unit ID、优先级、下一步证据和负责人；重要更正进入编纂队列，学习欠账进入补课队列，二者不要互相覆盖。

月度根据[能力地图](能力地图.md)和[研究队列](研究队列.md)检查七模块覆盖，分别统计有解释、能推导、有教学验证、有真实实验四类证据。轮换次数只是安排信息；“发现多少链接”“页面增加多少字”都不能用作掌握率或知识正确率。SWE-agent的后继推荐、AutoGen的归档公告等维护变化也需保留日期和版本，不能沿用旧课程命令。

当前自动流程仍不提供无人值守深度编纂、全文归档、完整历史补采、知识点级复习游标或跨实例事务保证。本指南补全的是人工编纂与复习协议；来源订阅、运行代码和CI配置沿用现有实现。
