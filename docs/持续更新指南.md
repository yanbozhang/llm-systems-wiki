# 持续更新指南

目标是每天处理一个具体主题，并将新的理解写回长期页面。首版已提供来源巡检和学习轮换；专题阅读、证据判断及页面编纂由维护者与助手共同完成。自动任务不会把订阅标题直接变成事实。

## 每周安排

| 上海时间 | 主模块 | 本轮主题 |
|---|---|---|
| 周一 | 模型网络 | 四个核心主题按四周轮换 |
| 周二 | 训练 | 同上 |
| 周三 | 推理 | 同上 |
| 周四 | Harness | 同上 |
| 周五 | 知识库 | 同上 |
| 周六 | 业务 Agent | 同上 |
| 周日 | 跨模块复盘 | 断链、证据、更正、积压及学习路径 |

GitHub Actions 配置为每日上海时间 08:00（UTC 00:00）巡检；平台调度可能延迟。必须仓库已启用 Actions 且工作流在默认分支上，才能触发。手动操作可在仓库 Actions 页面选择“每日来源巡检”并运行。

## 自动阶段

工作流始终使用默认分支的维护脚本，顺序读取已登记订阅，生成当日主题计划与来源候选。候选、成功检查点和运行记录写入独立的 `updates/candidates` 分支，正式知识页保留在 main。发布候选使用串行任务和正常快进推送；推送失败时不替换远端检查点，后续可重复处理同一候选键。

输入为 [feeds.json](../sources/manifest/feeds.json)。成功且解析有效才推进该源检查时间；重复项按内容键去重。changed 表示新候选，unchanged 表示成功检查但无新候选，partial_failure 和 failed 保留失败原因。订阅最多读取 2 MiB、单次超时 20 秒。

每次运行的候选分支中包含 `candidates/runs`、`latest.json`、`state.json`、`study-plan.json` 与 `baseline.txt`。Actions 另保留运行产物，便于远端推送失败时恢复。候选分支中的其他文件可能是较早知识基线；阅读正式内容始终回 main。

## 每日专题编纂

1. 读取当天计划，优先处理更正与已知缺口；没有新资料时可以补读已有资料。
2. 选择 2—5 份原始材料，实际阅读全文相关章节，记录版本和读取限制。
3. 形成一句“这次认识改变了什么”，列出证据及受影响页面。
4. 使用[更新模板](../templates/更新模板.md)修订来源、声明、关系与主题；同时检查关联对比与练习。
5. 运行结构检查并复核语义，再提交到 main。重要结论变化通过 PR 展示差异。
6. 在变化中心新增语义命名的记录，保留已处理候选 ID、无变化或拒收的理由。

没有证据支持的新结论可继续待研究；不要为了每日有新内容而重复改写原理。首次运行会建立订阅窗口基线，可能产生较多候选，应按主题筛选。

## 当前限制

首版发现范围是有限订阅窗口，尚无全历史分页或遗漏补采保证；不会自动判断 release 是否为正式版、条目是否具有知识变化，需阅读复核。工作流只自动维护候选，尚无每日无人值守 LLM 深度编纂。没有向量索引、Web 问答服务、数据库事务锁或跨实例恢复承诺。

本地维护入口是 `python scripts/wiki_tool.py check`、`plan` 与 `discover`；脚本仅依赖 Python 3.11+ 标准库。具体语义见[维护工具契约](../schema/维护工具契约.md)。
