# 结构优化与验收记录

日期：2026-11-25。分析基线：`f15013e`。本轮围绕系统优先阅读、Harness重组、GraphRAG/LLMwiki拆分、RSI新增，以及维护链路中的实际缺陷展开；未改动个人学习笔记或历史发布清单。

## 实际项目机制

1. **知识身份与内容分离**：`knowledge`登记模块、主题、知识点、声明、关系与能力，Markdown保存正文；来源清单登记读取范围、原生版本和本库指纹。二者共同驱动网站，不存在独立CMS。
2. **发现不等于发布**：每日任务读取订阅，写候选和检查点到独立候选分支，不自动更改已发布结论。`plan`只提供轮换建议，不追踪个人完成状态。
3. **可追溯来源库**：每条来源生成资料卡；可公开快照保留原许可，其他下载按字节SHA-256存入被Git忽略的本地缓存。普通离线检查与本机缓存完整性检查不同。
4. **静态网站**：Astro生成文章、模块、路径、研究与来源页面；Markdown先清洗原始HTML，再渲染数学和代码；Mermaid在浏览器按需串行绘制。收藏与语言偏好保存在浏览器本机。
5. **分层验收**：Python检查结构和教学模型，TypeScript检查搜索与转换，构建测试检查实际HTML与清单对应。以上均不能替代论文全文语义核验、真实模型实验或人工体验判断。

## 发现的问题与处理

| 问题 | 根因 | 本轮处理 |
|---|---|---|
| 模块入口缺少系统解释 | 模块Markdown没有被展示，页面主要是卡片与学习目标 | 八模块增加架构图和系统说明，网站先渲染系统总览，再显示有原文介绍的主题卡片 |
| 主题难以先形成整体认知 | 正文直接顺序展开，缺少清楚的知识点入口 | 保留原文导语作为总览，生成对应真实章节ID的细化阅读路线 |
| Harness概念与框架入口混在一起 | 只有横向主题列表，缺少职责和交接关系 | 增加M1—M8职责、执行/持久/改进闭环、六类交接记录，链接既有细化主题 |
| GraphRAG与LLMwiki共用一个主题 | 查询组织与持续编纂的学习目标耦合 | 保留旧GraphRAG路由，建立LLMwiki主题，迁移稳定知识点ID并同步声明、能力及学习路径 |
| 无法直接增加第八模块 | 模块校验和学习轮换绑定七个唯一weekday | 显式同日rotation_group按周交替；Harness/RSI各自按出现次数推进主题，周日仍为Benchmark |
| 索引损坏后反复失败 | 客户端只校验数组，已缓存的坏条目一直被复用 | 校验字段、ID和站内路由，失败清除缓存；可执行结果URL不能进入搜索列表 |
| 输入时重复处理全文 | 每次查询重新做Unicode规范化 | 预编译索引快照，多次输入只做匹配和排名；离线筛选保持同样的关键词语义 |
| 抓取存在地址检查与连接间隙 | 原文先检查DNS，再由默认传输重新解析；订阅只做部分URL检查 | 共用公网HTTPS传输，在连接时检查全部答案并直连数值地址，保留TLS主机名校验，禁用代理 |
| PR不执行网站检查 | 网站验收只在main部署流程中运行，Python单测也不是部署的完整门槛 | PR和Pages共用同一检查工作流，全部检查通过才部署 |
| 地图和数字易漂移 | 静态SVG和部分前端文案硬编码规模 | 页面数字从清单读取，知识/能力SVG由可检查的标准库脚本生成 |

## 搜索微基准

真实50主题索引，固定6组查询，预热后执行1200次。一次本机测量：

- 索引预处理：约2.49ms。
- 每次重新处理全文：约1245.83ms。
- 复用预编译索引：约77.88ms，约16倍。

两条路径逐查询比较结果一致。测量不包含网络、DOM渲染或用户输入等待，不应写成“整站快16倍”；不设置机器相关的时间阈值作为CI门槛。

## 兼容性与仍需验证的边界

- `/read/graph-wiki/`及原Markdown文件路径保留；`graph-wiki-wiki-impact`保留ID但归属改为LLMwiki，公开索引同步迁移。
- 原文抓取不再使用环境/系统代理；必须依赖代理的环境需另行设计显式受控出口，不能悄悄绕开公网边界。
- DNS解析仍受操作系统管理；本轮防护不是任意网络环境下的全方位隔离，也不替代部署网络策略。
- 教学示例与真实系统实验仍保持分离；RSI不执行任意候选代码，不自动训练模型或发布自改动。
- 静态图表、文字和来源都需持续维护；结构检查通过不能证明每条学术结论正确。
